# Mini Booking

Бронирование переговорной по часовым слотам. Комната работает каждый день с 9 до 18, это девять слотов в день. Страница на Vue и JSON API на Laravel живут в одном проекте: Vue собирается через Vite и обращается к API по относительным адресам `/api/...`.

Стек: Laravel 12, PostgreSQL, Vue 3 (`<script setup>`), PrimeVue 4, PHPUnit.

## Быстрый старт

Понадобятся PHP 8.2+ с расширением `pdo_pgsql`, Composer 2, Node.js 20.19+ или 22.12+ и PostgreSQL 12+. Я запускал на PHP 8.4, Node 22 и PostgreSQL 14 под macOS.

```bash
psql -d postgres -c "CREATE ROLE mini_booking LOGIN PASSWORD 'your-password'"
psql -d postgres -c "CREATE DATABASE mini_booking OWNER mini_booking"
psql -d postgres -c "CREATE DATABASE mini_booking_test OWNER mini_booking"

composer install
npm ci
cp .env.example .env        # вписать DB_PASSWORD
php artisan key:generate
php artisan migrate
php artisan db:seed
npm run build
php artisan serve
```

Страница откроется на http://127.0.0.1:8000.

При разработке вместо `npm run build` удобнее держать во втором терминале `npm run dev`. `artisan serve` читает `.env` только при запуске, поэтому после правки `.env` сервер надо перезапустить.

## Настройки

В `.env` только то, что отличается от машины к машине: `APP_ENV`, `APP_KEY`, `APP_DEBUG`, `APP_URL`, параметры подключения к базе и `APP_TIMEZONE`. Через `APP_TIMEZONE` задаётся часовой пояс расписания (`config('app.timezone')`), в примере стоит `Europe/Istanbul`.

Язык `ru`, соединение `pgsql`, файловые сессии и кеш от окружения не зависят и прописаны в `config/`.

## Расписание

`php artisan db:seed` вызывает `ScheduleSeeder`. Он создаёт слоты на сегодня и шесть следующих дней в часовом поясе расписания, на пустой базе выходит 63 слота. Сегодняшние слоты появляются все, даже если рабочий день уже прошёл, и на странице они отмечены как прошедшие.

Запускать Seeder повторно безопасно. Он вставляет строки через `INSERT ... ON CONFLICT DO NOTHING` по уникальному `starts_at`, так что существующие слоты сохраняют свои ID, а брони не меняются. Если запустить его на следующий день, добавятся девять слотов нового последнего дня. Сам по себе он не запускается, Scheduler в задании не нужен.

## Тесты

```bash
php artisan test
```

Тесты работают с настоящей PostgreSQL и базой `mini_booking_test`. Её имя прописано в `phpunit.xml`, хост, пользователь и пароль берутся из `.env`. `tests/TestCase.php` проверяет имя базы сразу при создании приложения, до `RefreshDatabase`, и останавливает тесты, если оно не заканчивается на `_test`. Имя берётся у самого соединения, так что проверка учитывает и `DB_URL`. Время в тестах заморожено через `travelTo`.

Два обязательных сценария лежат в `BookingApiTest`: бронирование свободного слота и повторный запрос на уже занятый слот, который получает 409 без второй активной брони. В `BookingRulesTest` собраны граничные случаи вроде слота, который начинается ровно сейчас, ошибок валидации и повторной брони после отмены. `ScheduleSeederTest` проверяет количество слотов, повторный запуск и запуск на следующий день.

## API

| Запрос | Ответы |
|---|---|
| `GET /api/slots` | 200 |
| `POST /api/bookings` | 201, 422, 409 |
| `DELETE /api/bookings/{id}` | 204, 404 |

```bash
curl http://127.0.0.1:8000/api/slots

curl -X POST http://127.0.0.1:8000/api/bookings \
  -H 'Accept: application/json' -H 'Content-Type: application/json' \
  -d '{"slot_id": 8, "customer_name": "Иван", "customer_email": "ivan@example.com"}'

curl -X DELETE http://127.0.0.1:8000/api/bookings/12
```

Ответ на `GET /api/slots`:

```json
{
  "data": [
    {"id": 1, "starts_at": "2026-11-17T06:00:00Z", "ends_at": "2026-11-17T07:00:00Z", "status": "past", "active_booking_id": null},
    {"id": 8, "starts_at": "2026-11-17T13:00:00Z", "ends_at": "2026-11-17T14:00:00Z", "status": "booked", "active_booking_id": 12}
  ],
  "meta": {"timezone": "Europe/Istanbul", "server_now": "2026-11-17T11:07:05Z"}
}
```

Статус слота считает сервер, причём для всего ответа берётся один момент `now`. Слот прошёл, если `starts_at <= now`, то есть ровно в момент начала его уже нельзя забронировать. Прошедший слот остаётся `past`, даже если на него есть бронь, но её номер в `active_booking_id` всё равно виден. Имена и почта в список не попадают.

Успешное бронирование возвращает `201 {"id": 12}`. Ошибки в полях приходят в стандартном формате Laravel с кодом 422:

```json
{"message": "Такого слота нет в расписании.", "errors": {"slot_id": ["Такого слота нет в расписании."]}}
```

Несуществующий `slot_id` тоже даёт 422. Если слот занят или уже начался, ответ будет 409 с причиной: `{"message": "Слот уже занят другим бронированием."}`. Отмена отвечает 204 без тела, повторная отмена тоже. На неизвестный номер брони приходит 404.

Авторизации в демо нет, так что отменить бронь может любой, кто знает её номер.

## Одна бронь на слот

Отмена не удаляет запись, а заполняет `cancelled_at`, поэтому история сохраняется. Активной считается бронь с `cancelled_at IS NULL`.

Две активные брони на один слот запрещает сама база, через частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX bookings_one_active_per_slot ON bookings (slot_id) WHERE cancelled_at IS NULL;
```

Индекс срабатывает при любой записи, в том числе в обход приложения. Отменённые брони в него не входят, и слот после отмены можно занять снова. Обычный `UNIQUE (slot_id, cancelled_at)` здесь не помог бы: в PostgreSQL два `NULL` не равны друг другу.

Перед вставкой `BookingService::book()` открывает транзакцию и блокирует строку слота через `SELECT ... FOR UPDATE`. Параллельные запросы на один слот выстраиваются в очередь, и второй видит бронь, которую создал первый. Время проверяется уже после блокировки, потому что за время ожидания слот мог начаться. Если индекс всё-таки сработает, приложение превратит это в 409 после отката транзакции, а другие ошибки базы не станут «слот занят».

Блокирую строку слота, потому что она уже существует, а строки брони ещё нет, и блокировать там нечего. Уровень изоляции `SERIALIZABLE` тоже решил бы задачу, но потребовал бы повторять транзакции при конфликтах.

## Время

База хранит моменты в `timestamptz`, соединение с PostgreSQL работает в UTC. Даты уходят в запросы со смещением: формат `Y-m-d H:i:sP` задан в грамматике соединения (`app/Database/OffsetPostgresGrammar.php`), и им пользуются и модели, и query builder. Со стандартной грамматикой Laravel локальные 09:00 по Стамбулу записались бы как 09:00 UTC.

API отдаёт время в UTC с `Z` на конце, а название часового пояса передаёт отдельно в `meta.timezone`: `timestamptz` его не хранит. Страница форматирует дату и время через `Intl.DateTimeFormat` в этом поясе, поэтому у человека с другим поясом в браузере часы не съезжают.

Например, Seeder записывает `2026-11-17 09:00:00+03:00`, в базе это 06:00 UTC, API отдаёт `2026-11-17T06:00:00Z`, а на странице видно 09:00.

## Интерфейс

Страница собрана из компонентов PrimeVue 4. Пятую версию брать не стал: она требует лицензионный ключ PrimeUI (бесплатный для небольших команд или платный), а без ключа на странице висит плашка «Invalid PrimeUI License». PrimeVue 4 распространяется под MIT и ключа не требует.

Запросы к API вынесены в `resources/js/api.js`, форма бронирования в `resources/js/components/BookingDialog.vue`. При ошибке 422 сообщения появляются у полей, при 409 диалог закрывается и расписание обновляется. Если ответ на создание брони потерялся, страница не отправляет запрос снова сама, а предлагает сначала обновить расписание.

## Проверка параллельных запросов

```bash
PHP_CLI_SERVER_WORKERS=4 php artisan serve --no-reload
scripts/concurrency-check.sh     # во втором терминале
```

Скрипт держит блокировку слота из отдельной сессии psql и в это время отправляет два POST. Затем он проверяет, что оба запроса ждали одновременно, ответы пришли 201 и 409, а активная бронь осталась одна. Флаг `--no-reload` обязателен: без него `artisan serve` запускает один воркер, и гонки просто не случится. После проверки в базе остаётся тестовая бронь, её можно отменить на странице.
